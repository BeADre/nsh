# 为运行时出现的新界面选择技术

Native Shell（NSH）让手机和桌面应用在发布后接收新的交互界面。它把可编程界面、动态模块加载、宿主组件组合与执行管理放进同一条开发路径：稳定的产品核心继续由宿主掌握，新的任务界面可以按需交付。

这对 AI 产品尤其重要。用户提出任务之后，应用才知道需要怎样的表单、列表、图表和操作流程。NSH 让结果成为带状态和行为的界面，使用客户端已经具备的业务服务与原生能力。

**选择 NSH 的主要理由，是产品需要持续接收新交互，同时保留现有客户端及其控制权。** 它也支持用 Rust 构建完整应用，并在需要时加入动态 TSX。这两条路径共享组件与核心引擎，动态能力可以是一个局部面板，也可以成为产品的主要交付方式。

## 从一个已经上线的客户端开始

假设你的产品已经有订单服务、登录状态、图表和手机、桌面客户端。用户现在提出一个发布前没有设计过的任务：

“比较这几份报价，补齐缺少的信息，选好交付方式，确认后保存订单。”

这不是把一段文字塞进聊天气泡。界面需要查询数据、保留选择、处理失败、根据输入改变下一步，并调用已有的保存订单接口。下一次任务可能又需要不同的流程。

有三种合理做法，成本落在不同地方：

| 你真正需要交付什么 | 合适的起点 | 需求增长时的工程工作 |
| --- | --- | --- |
| 已有页面的新数据、新布局或已知动作组合 | 服务端驱动 UI，或 Flutter RFW 等对应技术 | 维护组件与动作契约；新行为超出契约时，扩展宿主或表达语言 |
| 自己应用的一版新代码 | React Native 更新服务、应用发布或适用的代码补丁方案 | 管理应用版本、原生依赖兼容、测试与回滚 |
| 独立加载、带自身状态与逻辑的新任务模块 | NSH；也可在其他框架上搭建相应模块宿主 | 定义开放 API、模块来源及权限；NSH 提供包验证与 Surface 执行管理的基础 |

WebView 也是直接有效的选择，尤其适合已有网页、文档和 Web 组件。需要比较的是网页与原生服务、输入和视图的集成成本。NSH 面向的是希望通过客户端后端承载这些动态界面，并复用宿主组件的产品。

## NSH 如何把这次任务变成界面

**先开放能力，再交付流程。** 宿主提供“读取报价”“保存订单”和图表等接口；动态模块决定如何组合它们，管理当前选择、查询进度、校验和确认交互。订单权限、登录凭据和最终业务校验留在宿主或服务端。模块不需要获得整个应用的内部对象。

一个可交付版本可以沿着以下路径进入客户端：

1. 用类型化组件与 API 编写或生成 TSX，包含这次任务的布局、状态和事件逻辑。开发者可以用[开发工具](./cli.md)检查接口，并用[无界面 trace](./testing-and-trace.md)检查执行过程。
2. 将模块构建为 bundle；需要校验来源与版本的动态交付使用[签名包](./signed-packages.md)。宿主决定下载来源与更新时机，NSH 在打开签名包时执行信任、兼容版本、撤销与回滚检查。
3. 在页面中创建 Surface，并设置允许的能力和执行预算。原生端的动态 TSX Surface 各有 QuickJS VM 与引擎线程，界面更新交给对应平台后端。
4. 任务结束后卸载 Surface。宿主负责关联请求的取消及业务资源清理，也决定运行中模块何时需要停止或重载。

界面中的图表可以保留为 Rust 组件，也可以通过[原生组件注册](./native-components.md)接入宿主已有视图。动态模块负责组合，宿主提供属性、事件、命令与尺寸接口。新增原生二进制能力仍需更新宿主；模块只能调用已经存在且被开放的能力。

这条路径的产品意义是：**新流程可以单独交付，核心业务和复杂组件可以持续复用，模块接受什么权限由宿主决定。** 接下来比较其他框架时，要看实现这条路径需要保留什么、增加什么，以及这些工作是否值得。

## React Native：已有 React 产品继续更新；原生与 Rust 宿主按模块扩展

NSH 让已有原生与 Rust 客户端直接围绕可交付模块建立扩展接口，核心组件与业务实现继续留在宿主。

如果订单客户端已经用 React Native 开发，新面板可以写成 React 组件，通过 [EAS Update](https://docs.expo.dev/eas-update/runtime-versions/)交付兼容的 JS 和资源，继续调用已经安装的订单模块。这保留了 React 状态模型、组件库和原生扩展。仅仅因为界面由 AI 生成，并不足以换用 NSH。

NSH 更有吸引力的起点，是产品已有原生或 Rust 客户端，只想增加按需装入的任务界面。例如手机保留原生订单页，桌面保留 Rust 图表，只有“比较报价并确认”区域动态交付。宿主沿 NSH 的组件注册和 Rust 绑定接口开放能力，模块围绕这些接口组织交互。

RN 也支持[在原生应用中嵌入一个视图或流程](https://reactnative.dev/docs/integration-with-existing-apps)。真实的集成选择是：

- 走 RN 路线，将现有视图接到 [Fabric](https://reactnative.dev/docs/fabric-native-components-introduction)，将业务能力接到 Native Module，并围绕 React 的状态与组件模型维护动态区域。新架构通过 JSI 与原生实现协作。
- 走 NSH 路线，将宿主视图注册为组件，将 Rust 组件和业务类型开放给 TSX，并以 Surface 管理这块界面的执行。NSH 的信号组件模型并不直接兼容 React Hooks 或现成 React 组件。

因此，**已有哪一套组件资产，比“都能写 TSX”更能决定成本。** RN 团队往往能直接复用现有页面；Rust 或平台原生团队可以选择围绕现有实现建立 NSH 接口，而无需先将它们组织为 React 组件。

当产品需要安装多个独立来源的模块，交付单元也变得重要。EAS 解决的是某个 native runtime 对应的 JS/资源更新，并提供[签名验证](https://docs.expo.dev/eas-update/code-signing/)。NSH 将包接受策略与 Surface 能力、VM 预算衔接起来，给模块分别设置边界。RN 的 [ReactHost](https://github.com/react/react-native/blob/main/packages/react-native/ReactAndroid/src/main/java/com/facebook/react/ReactHost.kt)可以管理多个 Surface，Surface 本身并不等于独立 JS VM；模块的运行时分配与策略仍需在方案中明确。

RN 的嵌入能力也在演进：[Expo SDK 56](https://expo.dev/changelog/sdk-56)提供了实验性的 iOS 多应用嵌入路径。它是值得评估的现成方案，但应核对目标平台、版本和模块权限需求，并分别确认多实例与权限隔离的具体保证。

**怎么选：**主要交付自己的可信 React 页面，优先延续 RN。已有原生或 Rust 产品，要把可加载的交互模块作为长期扩展机制，NSH 的接口与执行单元更贴近这个目标。收益是少搭建一部分模块宿主基础设施，而不是 React 页面自动迁移。

## Flutter：先决定要下发 Widget 描述、应用补丁，还是一个新程序

NSH 可以把新的异步交互流程随模块交付，让宿主开放稳定业务 API，而无需提前实现每一种任务流程。

Flutter 最有吸引力的地方，是产品可以围绕一套 Widget、动画与绘制体系构建完整体验。如果报价流程是应用的固定核心功能，用 Dart 实现并复用现有 Widget，通常是最直接的路线。NSH 的优势出现在流程要在发布后持续变化，而且变化包含新的程序逻辑时。

以“报价过期后重新查询，保留仍有效的选择，再要求用户确认差额”为例，三条动态路线会产生不同的工作：

| 路线 | 这次交付的内容 | 新逻辑放在哪里 |
| --- | --- | --- |
| Flutter [Remote Flutter Widgets（RFW）](https://pub.dev/packages/rfw) | 远程 Widget 描述、数据及事件连接 | 利用描述语言支持的表达与宿主已提供的事件；查询与业务行为需要相应宿主支持，也可另外引入脚本机制 |
| Flutter 应用补丁，例如 [Shorebird](https://docs.shorebird.dev/code-push/) | 面向已有发布版本的 Dart 代码补丁 | 更新应用程序，遵守补丁与原生代码兼容边界 |
| NSH 动态模块 | 带状态、异步查询、校验和事件处理的 TSX | 模块组织新的流程，调用宿主已经开放的服务 |

如果宿主已经提供了这套完整流程，RFW 足以重新组合它。如果每次生成都带来新的流程分支，把所有可能行为提前做成宿主回调会让动作协议不断增长。NSH 允许把这种编排随模块交付：宿主维护稳定业务 API，而不是预先枚举每一种任务流程。应用补丁同样能改变程序，但它解决的是应用版本演进，不能直接替代独立模块的安装、卸载和授权契约。

第二个选择是**谁负责绘制以及如何复用已有 UI**。Flutter 通常由自身引擎绘制 Widget；把现有原生控件放入其中，需要[平台视图](https://docs.flutter.dev/platform-integration/android/platform-views)集成。NSH 使用各平台后端，并为宿主视图提供注册接口。已有原生地图、播放器或输入区域的产品，应验证具体的焦点、手势、布局和生命周期，而不是只比较截图是否相似。例如地图或相机预览，Flutter 的 Android 平台视图有不同合成路径，各自需要核对滚动、无障碍与设备条件；NSH 移动端注册的视图进入宿主视图层级，但属性与事件以数据跨界、事件异步，必须即时决定的手势仍应留在原生侧。现成 Flutter Widget 也不会因为接入 NSH 就能直接复用。

Flutter 本身支持 [add-to-app 和多引擎](https://docs.flutter.dev/add-to-app/multiple-flutters)，也可用 [dart:ffi](https://docs.flutter.dev/platform-integration/bind-native-code)调用 Rust。选择 NSH 的依据不是“Flutter 只能做整个 App”或“只有 Rust 才快”，而是需要哪种交付单元和组件边界。

**怎么选：**要围绕统一 Widget、动画和 Flutter 插件构建产品，Flutter 很合适。要在已有客户端里不断交付新的任务程序，并把现有原生/Rust 组件作为它的积木，NSH 更直接。两者都是完整应用的选项，差别在产品最频繁变化的部分由哪一层负责。

## GPUI：让 Rust 客户端多一种交付方式

对已有 GPUI 或 GPUI Kit 产品，NSH 最实用的角色是动态扩展层。

直接使用 [GPUI](https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md)时，订单面板的状态、元素和事件处理都是 Rust 应用的一部分。编译器可以检查调用关系，组件可以直接使用宿主实体与服务。这很适合编辑器、复杂桌面工具和稳定的核心工作流。

但用户提出的新流程如果发布前没有实现，就需要应用自己引入另一种表达机制：扩大数据驱动协议、加入脚本运行时，或交付新的应用版本。NSH 提供的是其中一条完整路径：在 GPUI 应用里放入 Surface，让新 TSX 模块描述流程，调用已经开放的 Rust 能力。

例如，产品的导航、订单模型和高频图表继续用 GPUI；用户生成的比较面板使用 NSH。同样，在编辑器中，文档模型、选区和撤销栈适合留在 GPUI；一次重构的参数和分步确认可以成为动态任务区。边界带来的具体工作，是检查模块读取的文档版本是否仍有效、异步结果能否应用，以及关闭面板时取消哪些任务，而不必为了一个动态区域重写整个客户端。当前 [NSH GPUI 后端](./gpui.md)基于 GPUI Fast，并维护自己的视图树；GPUI 宿主状态与动态树之间需要明确接口。已有任意 GPUI 组件也不能自动放入 NSH 树中，仍需核对相应适配能力。

**怎么选：**核心界面在编译时已知，直接 GPUI 最简单；核心是 Rust，但希望发布后增加用户工具、合作方模块或 AI 交互，组合 GPUI 与 NSH。这个选择增加了一层运行时边界，换来的是界面逻辑的独立交付能力。它不要求把整个产品改写成脚本，也不意味着原有 GPUI 界面自动适配手机。

## Qt：动态 QML 已经很完整，关键是你要构建什么样的宿主

NSH 将多来源界面的包接受、宿主授权和执行预算放在同一条模块路径上，适合把动态扩展作为产品的长期能力。

Qt Quick 是最值得认真比较的方案之一。它可以[动态加载 QML](https://doc.qt.io/qt-6/qtqml-javascript-dynamicobjectcreation.html)，使用属性绑定和 JavaScript 处理交互，并调用开放的 QObject 方法。订单比较面板完全可以这样实现；如果产品已经拥有 QML 组件与 QObject 业务接口，这些资产很有价值。

两者的分歧在于产品围绕什么边界组织。

**Qt Quick 的自然起点是一个 Qt 对象世界。** 新 QML 创建对象、绑定属性、连接信号，复用应用已经暴露的类型。对于桌面工作台，资产还包括 [Model/View](https://doc.qt.io/qt-6/model-view-programming.html) 中的数据模型、共享选择、排序代理和编辑委托。替换界面层也意味着重新连接这些协作关系。它适合 Qt 团队交付新的界面组件，以及在统一工具箱中管理应用。当主要问题是“怎样更快开发和维护自己的跨平台界面”，Qt 的控件、工具与平台模块值得优先考虑。

**NSH 的自然起点是一个接收模块的宿主。** 界面可以来自多个发布方，宿主选择接受哪些包、向这个 Surface 开放哪些能力、给它多少执行资源。包验证、运行时要求和执行预算有相应接口。Qt 官方的[安全模型](https://doc.qt.io/qt-6/shared-security-model.html)以可信应用代码为前提；把可下载 QML 发展为多来源扩展平台时，需要另行设计可信代码的接受范围和执行边界。NSH 把这部分需求提前纳入产品路径，但其进程内 VM 同样不等于操作系统沙箱。

一个具体判断是：合作方交付了新的报价面板，你是否愿意让它拥有当前 QML 环境中开放的能力？如果愿意，而且全部代码通过同一条可信发布流程，Qt 的动态组件可能已经满足需求。如果需要按模块减少网络范围、限制脚本资源并检查包版本，NSH 的现有管理接口会更有用。两边都仍需保护业务 API，卸载 UI 也不会撤销已经提交的订单。

Qt Widgets 则是另一个起点。[QUiLoader](https://doc.qt.io/qt-6/quiloader.html)可从 UI 描述创建已有控件，新业务行为仍需相应代码。Widgets 产品可以通过 [QQuickWidget](https://doc.qt.io/qt-6/qquickwidget.html)加入动态 Quick 区域，但会引入额外的离屏渲染步骤及渲染循环约束。这是需要评估的实际集成代价，而不是“Qt 能否动态加载”这种简单判断。

Rust 也不是二选一的分界线：Qt 可以通过 [CXX-Qt](https://kdab.github.io/cxx-qt/book/)等方案连接 Rust。**已有 Qt 产品，优先衡量保留 QObject/QML 资产的收益；已有原生或 Rust 宿主，要把动态模块交付与执行管理作为产品能力，重点评估 NSH。**

## Slint：UI 与宿主行为分工明确，还是让任务模块自己编排流程

NSH 让可交付的 TSX 同时承担界面和任务编排，适合新需求经常包含查询、等待、重试和分步确认的产品。

Slint 与 Rust 配合紧密，既能编译 UI，也有[解释器](https://docs.slint.dev/latest/docs/rust/slint_interpreter/)在运行时加载 `.slint`。其语言支持绑定、条件、表达式和回调逻辑，能够表达动态交互。

真正有用的比较，是新的业务流程放在哪里。

如果报价面板只是展示数据、切换选择，并触发宿主已有的“提交订单”回调，Slint 的动态组件可以很好地承担这项工作。Rust 负责服务、任务与业务状态，UI 通过属性和回调协作。边界明确，也容易继续复用已有 Slint 组件。

再向前一步：新模块要并行查询几个来源、处理部分失败、等待用户修正，再决定调用哪一个宿主操作。使用 Slint 时，要判断这些编排由 UI 语言承担多少、由 Rust 回调承担多少；解释器加载新的 UI 并不会同时下载新的 Rust 实现。使用 NSH 时，TSX 模块可以用通用脚本和异步逻辑组织这段流程，Rust 只开放稳定的查询和保存 API。

**因此，差异不在于有没有动态加载，而在于每次新任务需要扩展多少宿主行为。** 产品的变化主要是 UI，既有回调契约稳定，Slint 的分工很自然。变化经常包含新的任务编排，NSH 可以把更多变化保留在可交付模块中。代价是动态部分带上脚本运行时，需要管理生成代码；稳定核心仍可保留 Rust。

对于图表等能力，两边都能利用 Rust。Slint 可以把 Rust 生成的像素通过 [Image / SharedPixelBuffer](https://docs.slint.dev/latest/docs/rust/slint/struct.Image)显示，并用属性和回调连接数据；NSH 可以开放 Rust 组件或注册宿主视图。实际选型应验证需要复用的是计算函数、绘制结果还是可交互组件，它们需要的适配并不相同。

**怎么选：**Rust 产品需要清晰的 UI/业务分工，尤其已有 Slint 组件时，Slint 很有吸引力。要交付带独立编排逻辑的任务模块，并把宿主能力组合成新的交互，NSH 的模块语言与执行路径更贴合。

## 完整应用也可以从 Rust 开始

NSH 的动态能力并不要求应用把核心功能交给 JavaScript。用 [Rust 构建完整应用](./rust.md)时，UI、状态和业务可以全由 Rust 实现，完全不链接 QuickJS。原生平台上的这些实现编译为本机代码，可以使用 Rust 的类型检查、内存管理和底层优化能力。

混合应用则选择另一种分工：图表、编辑器、数据处理和稳定业务继续编译，TSX 只承担经常变化的页面和任务流程。两者共享 NSH 的组件与响应式核心，通过明确接口组合。先写完整 Rust 应用，之后再为某个区域加入动态交付，是一条可选择的演进路线。

这也说明了怎样评估性能：应测量具体的布局、文本、绘制、跨边界调用和任务负载。原生 Rust 核心不受 JS 执行吞吐量支配，但仅凭实现语言不能推出整个应用比其他框架更快。

## 平台与执行边界，需要一起选择

NSH 的组件抽象由各端后端承载：iOS 使用 UIKit/CoreText，Android 使用 Android Views 和平台输入能力，macOS 使用 AppKit/Core Animation/CoreText，Windows 使用 Win32/Direct2D/DirectWrite，Linux 使用 GTK 4/GSK/Pango；GPUI 后端用于 Rust 桌面宿主，Web 呈现 HTML/DOM。具体接入和支持范围见[平台指南](./platforms.md)。共享组件不意味着所有控件都是系统控件，也不保证各端行为完全一致。

[Web 路径](./web.md)需要单独理解：动态 TSX 仍使用 QuickJS，纯 Rust 可以移除它；两者都通过 Web 后端呈现 HTML。浏览器本地引擎在页面线程执行，原生 Surface 的线程安排不能直接套到 Web。

接受生成代码时，还应明确以下边界，详见[能力与资源限制](./sandbox-and-capabilities.md)：

- 签名证明来源与完整性，不证明行为安全。QuickJS 字节码需要可信来源，例如验证后的包；进程内 VM 不提供操作系统进程隔离。
- 能力策略要明确配置。省略模块能力声明不等于拒绝所有访问；宿主授权和模块声明共同决定受管理能力的有效范围。
- VM 堆、栈、调用时间和节点限额不覆盖任意宿主原生函数的全部 CPU、内存或 GPU 开销。业务授权、耗时操作和取消仍由宿主负责。
- 宿主获取撤销信息并决定运行中模块的处理方式。包打开时的撤销检查不等于远程立即终止，移除界面也不回滚业务副作用。

动态模块还必须遵守目标平台的分发政策。以上是实现边界，不是绕过原生发布或平台审核的途径。

## 最后，按你要保留的核心来选

| 产品的起点与目标 | 更值得优先评估的路线 |
| --- | --- |
| AI 生成的界面包含新的查询、校验与分步操作 | NSH 将界面与任务逻辑作为一个模块交付 |
| 合作方扩展需要独立版本、权限和执行预算 | NSH 的签名包、Surface 与宿主策略接口 |
| 已有原生或 Rust 客户端，希望复用核心并持续加入新界面 | NSH 动态模块与宿主组件组合 |
| 希望完整 UI 与业务使用 Rust，并按区域选择是否动态化 | NSH 的纯 Rust 或 Rust + TSX 路径 |
| 已有 RN 组件和团队，持续更新自己的移动页面 | RN 与现有更新服务 |
| 用统一 Widget、动画和插件体系建设完整产品 | Flutter |
| Rust 桌面核心稳定，需要直接的类型与组件协作 | 直接 GPUI；出现运行时扩展需求时组合 NSH |
| 已有 QObject/QML/Widgets 资产，主要运行可信应用代码 | Qt；多来源模块需求单独评估执行边界 |
| Rust 业务与 UI 属性/回调分工稳定，已有 Slint 组件 | Slint，包括其运行时解释器 |

NSH 最明确的价值，是把“发布之后才出现的界面”变成客户端可以接收、组合和管理的单元。对需要 AI 交互、动态业务页面或扩展模块的产品，这直接影响新功能怎样到达用户，也决定了哪些能力可以长期留在稳定的原生核心中。

本文依据 2026 年 10 月 19 日的 NSH 实现与所链接的一手资料；方案中的工程取舍是基于这些机制的分析，并非跨框架性能基准。
