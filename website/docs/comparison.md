# Native Shell and cross-platform UI frameworks

Native Shell (NSH) is a cross-platform UI engine designed for **AI-generated interfaces and dynamic delivery**. Applications can load new interactive interfaces at runtime, combine them with existing pages, business services and native components, and let the host manage code provenance, permissions, resource limits and lifecycle.

Our starting point is to let mobile and desktop applications host interfaces created after the application ships: interactive panels generated by AI for a task, business pages delivered on demand, partner modules and user-installed extensions. These interfaces can carry their own state, logic and interactions while using the native capabilities exposed by the host.

NSH also supports complete mobile and desktop clients. An application can combine dynamic modules, compiled Rust components and platform-native interfaces. Performance-sensitive UI and business logic can be implemented directly in Rust, and pure Rust applications can omit QuickJS entirely.

## The problem we start with

Traditional applications usually define their pages and features before release. AI changes that sequence: the best interaction may only become clear after a user asks for something. One result might call for a form; another might need a filterable data list, a chart, step-by-step confirmation or an actionable detail page.

NSH provides a complete path for generating and delivering interfaces at runtime:

| Core need | What NSH provides | Value for the application |
| --- | --- | --- |
| AI-generated interactive interfaces | Typed components and APIs; TSX modules with state, logic and event handlers | An AI result can become an interface the user can act on |
| New interfaces delivered at runtime | Dynamic loading, signed-package verification, runtime compatibility and version checks | Pages and modules can be delivered independently of the host binary |
| Composition with existing applications | Native host embedding and access to registered components and business APIs | Add dynamic interfaces incrementally to an existing product |
| Boundaries for dynamic code | A separate VM for each native dynamic surface, execution budgets and host capability policies | Manage trust and access boundaries between modules and the host |
| Mobile and desktop clients | Platform backends, shared component abstractions and platform-specific interaction support | Use the same dynamic interface model across clients |
| A compiled implementation path | Rust components, business modules and complete Rust applications | Keep core features in compiled code and use dynamic modules to compose them |

Dynamic delivery here means loading new interface modules and their behavior while an application is running. It goes beyond switching existing controls based on data and serves a different purpose from development hot reload. The host handles downloads and update timing; NSH handles loading, verification and execution. New native binary capabilities still go through the host's build and release process. Application distribution must also follow the target platform's policies.

## Other ways to deliver dynamic interfaces

WebViews, server-driven UI and application code updates all support dynamic content. NSH brings programmable interaction, native host composition and module execution management into one workflow.

| Approach | How the interface is expressed | What the application manages | The option NSH provides |
| --- | --- | --- | --- |
| WebView pages | HTML, CSS and JavaScript, laid out and presented by the browser | Web/native interfaces, navigation, interaction coordination and authorization | Present modules through platform backends and call host-registered components and services |
| Server-driven UI | Schemas, components and action protocols supported by the host; state and expression support depend on the protocol | The component catalog, protocol versions and supported behavior | Use programmable modules to organize state, asynchronous work and interaction while reusing host capabilities |
| Application code updates | Updated code and assets compatible with the installed runtime | Update compatibility, the scope of trusted code and the application's release model | Manage interface module execution and lifecycle at the surface level |
| NSH dynamic modules | TSX modules and host components compose an interaction | Available components, business APIs, provenance, permissions and resource budgets | Generate and deliver actionable interfaces for individual user tasks |

These approaches can work together. A WebView suits documents or existing web pages; a schema may be sufficient for a stable, predictable form. NSH focuses on tasks that need new interaction logic, with modules that reuse existing client capabilities and run under the host's execution policies.

## Ways to compose dynamic interfaces

NSH can power a region, a page, an extension or an application's entire interface. The host decides which capabilities to expose, and modules use those capabilities to carry out specific tasks.

| Composition | Example | NSH's role |
| --- | --- | --- |
| Native client with AI-generated interfaces | A chat result includes a filter form, result list and action panel | Turn an AI task into an interactive client interface |
| Existing business page with a dynamic module | An order detail page loads a context-specific tool or explanation panel | Extend part of a page while reusing its structure and services |
| Rust components with dynamic pages | TSX organizes interactions around compiled charts, editors or data-processing capabilities | Retain the core implementation while delivering new page compositions |
| GPUI client with dynamic extensions | Embed an NSH surface in a GPUI or GPUI Kit application | Add a dynamic interface layer to an existing Rust desktop product |
| Stable core with optional plugins | Ship the core as compiled code and load selected tools or workflows on demand | Let core features and extension modules evolve at their own pace |
| Standalone client | Build a complete application with Rust, TSX or a mixture of both | Use the same core component capabilities for dynamic modules and complete applications |

The [iOS](./embedding-ios.md) and [Android](./embedding-android.md) embedding APIs connect NSH to native hosts; the [GPUI backend](./gpui.md) provides a Rust desktop integration path. [Native component registration](./native-components.md) lets hosts supply component factories, properties, events, commands and sizing coordination. Component implementation and business authorization remain the host's responsibility. Dynamic modules use capabilities the host has already provided.

## Execution boundaries for generated code

AI-generated interfaces need more than a renderer. An application also needs to establish where code came from, what it can access and how many resources a misbehaving module can consume. NSH includes these concerns in module delivery and execution.

| Boundary | NSH mechanism | What the host manages |
| --- | --- | --- |
| Provenance and integrity | Signed packages, trust roots, release certificates and file verification | Which publishers' modules to accept |
| Versions and compatibility | Revocation, minimum runtime versions and rollback protection | Accepted module versions and runtime requirements |
| Execution environment | A separate QuickJS VM for each native dynamic surface | Script state and lifecycle for each surface |
| Execution resources | Limits on heap, stack, call duration, nodes and queued operations | Budgets for selected execution and interface resources |
| Platform capabilities | Module capability declarations that the host can further restrict | Managed access such as network destinations, WebView navigation and the clipboard |
| Business capabilities | Host-registered components and business APIs, with host-enforced authorization | Which product operations a module can perform |

[Signed packages](./signed-packages.md) verify provenance and integrity; [runtime limits and capability policies](./sandbox-and-capabilities.md) constrain execution. Configure an explicit policy for restricted modules: an omitted capability declaration adds no restrictions at the module-declaration layer. Effective access must still satisfy the host's grant, and resource limits apply independently.

Custom native and business APIs exposed by the host must perform their own authorization checks. A VM provides an in-process boundary rather than operating-system process isolation; a signature establishes provenance and integrity rather than behavioral safety. QuickJS bytecode must come from trusted inputs, such as a verified package. Evaluate the complete host and its exposed capabilities when defining the trust boundary. The host must fetch revocation lists and update the trust store; revocation is checked when a package is opened. The host still decides when to stop or reload an already-running module. Signature revocation is not an immediate remote termination mechanism.

## Comparing the same tasks

The following sections use three tasks to examine what each framework provides and what the host still needs to implement:

1. **Generate a new interaction:** after the application ships, AI generates an order confirmation form with validation, asynchronous queries and confirmation logic. The form calls the host's existing save-order API.
2. **Manage partner modules:** load two modules from different sources at the same time, give them different network permissions and execution budgets, and reject revoked packages.
3. **Reuse a Rust core:** retain a compiled chart or computation service, let a dynamic interface control its parameters and display results, and handle component teardown and asynchronous callbacks correctly.

These tasks test expression and delivery, execution policies, and native integration, respectively. A dynamic language and module authorization are separate capabilities. Calling Rust and embedding an existing UI also involve distinct integration work.

For dynamic TSX on native platforms, NSH assigns a QuickJS VM and engine thread to each surface. Rust implements the signal graph, component core and layout, and each commit produces a mount batch. Web uses a local engine on the page thread, so the native threading boundaries do not carry over to Web. VM call-duration and heap limits do not bound the full CPU and memory use of arbitrary native host functions; host APIs need their own budgeting and cancellation design. See the [architecture](./architecture.md) and [execution limits](./sandbox-and-capabilities.md).

## How the framework directions differ

Based on implementations and official documentation as of October 19, 2026, the following comparison examines the mechanisms each framework provides and the work left to the host. NSH focuses on connecting generation, delivery, composition and execution boundaries into one module workflow. Performance still needs to be measured in the actual product.

| Framework | Main design focus | Dynamic interface path | NSH's emphasis |
| --- | --- | --- | --- |
| **NSH** | AI-generated interfaces, dynamic delivery and host composition, with support for complete applications | Module loading, signed packages and host-managed execution | Interface module delivery and execution as a coordinated set of capabilities |
| React Native | Native applications and extensions built with React | JavaScript modules, update services and native components | Independently managed surfaces, combining a Rust core with dynamic modules |
| Flutter | A shared widget, animation and rendering system | Runtime widget composition, server-driven UI and third-party updates | Hosting interface modules delivered for individual tasks |
| GPUI | Rust code-driven GPU UI, primarily used on desktop, with an upstream browser path | Dynamic modules supplied by the application or an additional runtime | Adding a dynamic layer to existing Rust clients and providing mobile backends |
| Qt Quick | QML, property bindings and a scene graph | Dynamic loading and creation of QML components | Workflows organized around module provenance, permissions and delivery |
| Qt Widgets | A mature desktop widget and application toolkit | Dynamic widget creation through application code | Deliverable interaction modules for mobile and desktop |
| Slint | Compilable declarative UI connected to Rust, C++ and other application logic | Compiled UI or runtime loading through the interpreter | TSX modules combined with host capabilities, signed delivery and resource budgets |

### Compared with React Native: both deliver JavaScript, but where is the module boundary?

React Native can also embed in an existing application, run newly delivered JavaScript and call installed native capabilities. NSH brings module execution, capability and delivery boundaries together around a surface. With React Native, the host organizes the corresponding policies around the React runtime and update services.

| Dimension | NSH mechanism | React Native mechanism | Practical difference and integration cost |
| --- | --- | --- | --- |
| Runtime and scheduling | Each native dynamic surface has a QuickJS VM and engine thread that submits batches to the UI thread | Typically uses [Hermes](https://reactnative.dev/docs/hermes); the New Architecture uses [JSI for native interoperability](https://reactnative.dev/blog/2024/10/23/the-new-architecture-is-here), and React scheduling can prioritize updates | Both let JavaScript drive native UI. NSH uses the VM as a surface boundary; React scheduling and limits on arbitrary script execution time are separate concerns |
| State, layout and mounting | A Rust signal graph tracks dependencies and updates bindings after component initialization; Taffy performs layout, followed by a MountBatch commit | [Fabric](https://reactnative.dev/architecture/render-pipeline) uses React updates to build a C++ shadow tree, Yoga for layout, then diffs and mounts host views | Both provide native layout and batched mounting. NSH uses signals rather than React's re-render model; moving React Hooks and components requires more than changing imports |
| Relationship between surfaces and runtimes | Each native dynamic surface has its own VM, state and execution budget | [ReactHost](https://github.com/react/react-native/blob/main/packages/react-native/ReactAndroid/src/main/java/com/facebook/react/ReactHost.kt) manages a ReactInstance and multiple surfaces; a surface by itself does not imply a separate VM | NSH assigns module budgets to an explicit unit. React Native can use separate runtimes, with the host planning shared modules, state and teardown relationships |
| Delivery of new interactions | Bundles or signed packages carry module behavior and use existing host APIs | [EAS Update](https://docs.expo.dev/eas-update/runtime-versions/) delivers JavaScript and assets matched to a native runtime version | Both can update logic built on existing native capabilities; new native APIs require a host upgrade in both. Application update versions and independent partner-module versions need separate designs |
| Signing and module policies | Package verification, revocation and rollback checks combine with intersected surface capabilities and VM limits | EAS also provides [update signing](https://docs.expo.dev/eas-update/code-signing/); a signed update does not automatically define per-surface permissions and budgets | NSH's distinction is restricted execution after verification; signing is available in both. A React Native host needs additional module-level authorization, revocation and resource policies |
| Native UI and Rust | Hosts register component properties, events and commands; Rust components and business types can be exposed to TSX | [Fabric native components](https://reactnative.dev/docs/fabric-native-components-introduction) integrate through typed specifications and Codegen; a [C++ TurboModule](https://reactnative.dev/docs/the-new-architecture/pure-cxx-modules) can adapt a Rust ABI | Both can reuse Rust computation. NSH's Rust core reduces cross-language implementation layers; React Native still needs Rust/C++ or platform adapters and object lifecycle management. Existing native views need integration in both |
| Platforms and existing code | NSH backends share a component model, with HTML presentation on Web | React Native core targets iOS and Android, with Web and other targets supplied by [ecosystem platform implementations](https://reactnative.dev/docs/next/out-of-tree-platforms) | NSH provides a shared module path. Existing React Native component libraries, Hooks and native dependencies remain valuable assets that need individual review during migration |

**Generating the same order confirmation interface:** React Native can deliver new JavaScript through an update mechanism and call an existing save-order module; NSH can deliver a surface package carrying that interaction. For updates to your own trusted application, React Native's established update workflow already fits. When several task modules from different sources share a screen with different permissions, NSH provides more direct places to attach budgets and policies. A React Native host needs to add those rules to its runtimes and host interfaces.

**Revoking the same partner module:** both need the host to obtain current policies and decide when to unload a running interface. NSH defines package revocation checks and surface budgets. React Native's runtime and surface lifecycles provide a foundation, with package policies designed separately. Multiple instances are available beyond NSH: [Expo SDK 56](https://expo.dev/changelog/sdk-56) provides an experimental path for embedding multiple applications on iOS, which should be evaluated against the version in use.

### Compared with Flutter: application patches, remote widgets or executable task modules?

Flutter's widget, layout and rendering system suits complete cross-platform applications; NSH focuses on bringing new interaction modules into an existing host. Flutter can combine update services, remote widgets or an additional execution engine. NSH provides executable task modules as a ready-made unit, giving the host a different set of integration responsibilities.

| Dimension | NSH mechanism | Flutter mechanism | Practical difference and integration cost |
| --- | --- | --- | --- |
| Runtime and scheduling | Native surfaces use QuickJS engine threads; the Rust core submits mount batches | Native releases use AOT-compiled Dart; current native platforms default to [merged UI and platform threads](https://docs.flutter.dev/release/breaking-changes/linux-merged-threads), with rasterization handled separately and [isolates](https://docs.flutter.dev/perf/isolates) available for computation | NSH separates module scripting from mounting. Flutter already provides a compiled execution path, so choosing Rust alone establishes no speed advantage over Dart |
| State and layout | Signals update bindings, and Taffy lays out the core tree | [Widget builds, Element identity and RenderObject layout and painting](https://docs.flutter.dev/resources/architectural-overview) work together, with layout based on parent constraints and child sizes | Component models and layout conventions differ. Using a Flutter widget as an NSH component requires adaptation |
| Controls and presentation | Platform views on mobile, backend-specific drawing on desktop, and HTML on Web | Controls are typically drawn by the Flutter engine; platform views embed host controls | Flutter provides a unified drawing and animation system. NSH follows each host's presentation path more closely, while platform behavior still needs verification |
| Multiple interfaces and lifecycle | Each native dynamic surface has its own VM, lifecycle and budget | [FlutterEngineGroup](https://docs.flutter.dev/add-to-app/multiple-flutters) supports multiple engines with independent state while sharing reusable resources | Both support partial embedding and multiple instances. Independent state alone defines no partner-package permissions; NSH also attaches execution policies to the surface |
| Delivery of new interactions | TSX packages deliver layout, state, asynchronous logic and events together | [RFW](https://pub.dev/packages/rfw) downloads widget descriptions and data and invokes host-provided events; it can be combined with scripting. [Shorebird](https://docs.shorebird.dev/code-push/) provides Dart code patches | RFW's callback scope, application patches and independent task modules are different delivery units. NSH directly defines executable modules, while the host still needs to expose sufficient business APIs |
| Update compatibility and policies | Check packages, runtime requirements, revocation and rollback; configure capabilities and budgets per surface | Flutter core relies on [third-party code push](https://docs.flutter.dev/resources/faq#does-flutter-support-code-push); patches depend on the corresponding release, and native dependencies must already be installed | NSH brings module acceptance and execution policies together. A Flutter host needs to design module-level trust and limits for its chosen RFW, patching or scripting path |
| Rust computation and native components | Rust components and modules integrate with the NSH core and its binding APIs | [dart:ffi](https://docs.flutter.dev/platform-integration/bind-native-code) can call a Rust-exported C ABI directly; native views use separate platform-view integration | Both can call Rust directly, without requiring a serialized message bridge. FFI addresses the computation interface; a chart's widget, rendering and teardown integration remain separate work |
| Web integration | HTML/DOM presentation, with a separate choice between TSX execution and the pure Rust path | [Flutter Web multi-view embedding](https://docs.flutter.dev/platform-integration/web/embedding-flutter-web) attaches to host DOM elements while retaining Flutter's internal presentation system | Both embed in existing web pages. The distinction is whether the interface itself uses the DOM or Flutter's drawing and component model |

**Generating the same order confirmation interface:** RFW suits compositions of widgets and events already provided by the host. New validation, queries and workflow logic require checking whether existing callbacks can express them, or introducing scripting or code patches. An NSH TSX package carries that logic directly, fitting tasks that each need a different programmable interface.

**Reusing the same Rust chart:** Flutter can call the computation core through FFI, then present it using Flutter drawing or a platform view. NSH can keep drawing and business logic in a Rust component, with TSX handling composition. Both execute native Rust; the difference is where component and lifecycle boundaries sit. Choosing NSH also requires evaluating replacements or adapters for existing Flutter controls, animations and plugins.

### Compared with GPUI: compiled Rust views or dynamic surfaces inside a host?

[GPUI](https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md) stores state in Rust `Entity` values, constructs element trees through `Render` and draws them with the GPU. NSH's [GPUI backend](./gpui.md) currently uses GPUI Fast: the surrounding application remains GPUI, with an NSH surface maintaining its own view tree inside it. The key questions are what this runtime layer provides and what it adds to the integration.

| Dimension | NSH mechanism | Using GPUI directly | Practical difference and integration cost |
| --- | --- | --- | --- |
| Delivering new interactions | Load TSX bundles that use components and services compiled into the host | Rust views and event handlers are compiled with the application; the application chooses and implements any additional dynamic layer | NSH can deliver new task logic after release. Direct GPUI retains more immediate Rust type and call relationships |
| State and updates | A Rust signal graph tracks bindings and updates them according to their dependencies after component initialization; the core maintains a shadow tree and uses Taffy for layout | `Entity` manages state; views use `Render` to produce elements for GPUI layout and drawing | NSH's reactive boundary sits inside the surface. Synchronizing host `Entity` state with module state requires explicit interfaces |
| Scheduling and drawing | A desktop surface's engine thread handles scripting, text and layout, then submits batches to GPUI's main thread; one surface element draws the internal retained tree | UI operations follow GPUI context and foreground-execution rules; background work uses its executors | NSH separates module logic from mounting while adding its own layout, event and data-conversion paths. Overall performance still requires measurement |
| Components and lifecycle | `AppView` manages the surface; the host chooses the embedding point and exposed capabilities | GPUI elements, views and Rust objects compose directly within one application model | Wrapping a dynamic region is straightforward. Placing an arbitrary existing GPUI component inside the dynamic tree requires adaptation beyond importing its crate |
| Module policies | Configure signature verification, revocation checks, capability policies and VM budgets through NSH | GPUI views and executors are application infrastructure; independent package trust, script runtimes and permission policies are designed by the application | NSH provides a ready-made management unit for task extensions. A fully trusted Rust core can keep its compiled execution model |
| Platform boundaries | The same module model also works through NSH mobile backends and its Web path | Upstream provides desktop backends and [browser examples](https://github.com/zed-industries/zed/blob/main/crates/gpui/examples/README.md) | NSH's mobile integration comes from separate backends. Existing GPUI desktop interactions still need adaptation for mobile |

**Applying both to the same task:** an existing GPUI Kit application needs to display a newly generated order confirmation panel. With NSH, the surrounding navigation and data services remain in Rust while the application loads just the panel logic. When the panel can be fully implemented ahead of time, direct GPUI components usually remove a layer of state, layout and event boundaries. Both approaches can retain a compiled Rust chart. NSH adds the ability for runtime modules to call it; the Rust implementation itself remains compiled in either case.

Scheduling references: [GPUI executors](https://github.com/zed-industries/zed/blob/main/crates/gpui/src/executor.rs), [NSH architecture](./architecture.md) and the [GPUI backend](./gpui.md).

### Compared with Qt: dynamic QML already exists; trust and host boundaries matter

Qt Quick and Qt Widgets deserve separate treatment. Quick's QML already provides dynamic objects, property bindings and JavaScript behavior. Widgets provides QWidget objects and a layout toolkit, with UI-file loading as well. NSH's more useful distinction is how modules from different sources are accepted and how they call the host.

| Dimension | NSH mechanism | Qt Quick / Qt Widgets mechanism | Practical difference and integration cost |
| --- | --- | --- | --- |
| Dynamic expression | TSX bundles carry state, asynchronous logic and events, loaded through a surface | Quick can [load QML files or dynamically compile strings](https://doc.qt.io/qt-6/qtqml-javascript-dynamicobjectcreation.html), including JavaScript handlers; Widgets uses [QUiLoader](https://doc.qt.io/qt-6/quiloader.html) to create controls of existing types | Quick can also generate new interactions. For Widgets, UI descriptions and new program logic are separate layers. NSH's distinction is the module execution contract |
| State and layout | A Rust signal graph, Taffy flex/grid layout and mount batches | QML [property bindings](https://doc.qt.io/qt-6/qtqml-syntax-propertybinding.html) update by dependency, with anchors/Layouts for layout; Widgets uses [QLayout](https://doc.qt.io/qt-6/layout.html) to manage control sizes | Both QML and NSH provide fine-grained dependency updates. Their components, layout rules and business object models differ; being reactive alone establishes no performance advantage |
| Execution and rendering | Native surfaces put scripting and layout on an engine thread; platform backends handle presentation | The QML engine executes bindings and handlers and supports [compiler optimizations](https://doc.qt.io/qt-6/qtqml-qtquick-compiler-tech.html); Quick's scene graph has [single-threaded and threaded render loops](https://doc.qt.io/qt-6/qtquick-visualcanvas-scenegraph.html), while Widgets UI runs on the main thread | NSH's boundary is the surface commit; Quick's is between GUI objects and the scene graph. Native extensions must respect each framework's threading requirements |
| Trust and budgets | Capability checks and VM heap, stack, call-duration and node limits still apply after package verification | Qt's [security model](https://doc.qt.io/qt-6/shared-security-model.html) assumes trusted application code and does not support treating untrusted QML as an isolated domain. Qt also provides a [QJSEngine interruption API](https://doc.qt.io/qt-6/qjsengine.html) | Qt can support a controlled script host, with additional design for independent module authorization, limits and isolation. NSH includes some of these policies in its module APIs, with in-process rather than process-level isolation |
| Host objects and teardown | Hosts register component factories, properties, events and commands; surfaces manage dynamic trees, while business resources have separate authorization and cancellation rules | QML uses QObject properties, signals and methods under [C++/QML ownership rules](https://doc.qt.io/qt-6/qtqml-cppintegration-data.html); Loader can destroy a subtree | Both can unload UI. Reversing an already-issued business operation is a separate responsibility, so ownership of objects and asynchronous tasks must be explicit |
| Rust and existing UI | Rust components and business types integrate directly with NSH; existing platform views use registration APIs | Bridges such as [CXX-Qt](https://kdab.github.io/cxx-qt/book/concepts/generated_qobject.html) connect QObject and Rust. [QQuickWidget](https://doc.qt.io/qt-6/qquickwidget.html) embeds Quick in Widgets, adding an offscreen rendering step and affecting the rendering thread model | Qt can reuse Rust and has concrete embedding trade-offs. NSH fits existing Rust/native hosts; Qt products retain their established QObject, widget and tooling investments |
| UI modules and binary plugins | Dynamic packages use existing host capabilities; new native implementations ship with the host | Loading QML source and loading shared-library plugins through [QPluginLoader](https://doc.qt.io/qt-6/qpluginloader.html) are separate paths; the latter has platform and ABI deployment requirements | Both must distinguish interface logic from native capabilities. NSH signed packages are a UI-module format, with native implementations supplied by the host |
| Browser presentation | The Web backend produces HTML/DOM | [Qt for WebAssembly](https://doc.qt.io/qt-6/wasm.html) supports Widgets, QML and Quick through browser rendering, subject to platform limits | Both support the browser. NSH differs in its DOM integration; complete accessibility behavior still needs explicit verification |

**Generating the same order confirmation interface:** Qt Quick can load QML containing JavaScript and call exposed QObject methods, overlapping with NSH's expressive goals. For code delivered by one trusted team, Qt already has a comprehensive dynamic component and business object model. When accepting code from multiple partners or generated by models, Qt's documented trust assumptions become central. The host needs additional acceptance policies and execution boundaries. NSH already exposes APIs for package verification, capability intersection and VM budgets as part of that workflow.

**Revoking the same module:** Qt Loader can remove an interface, and QJSEngine can interrupt execution. NSH provides package revocation checks and per-surface limits. Both still require the host to handle in-flight native calls and business side effects. NSH's value is to connect these acceptance and execution policies into a module workflow.

### Compared with Slint: both work with Rust; delivery languages and module policies differ

Slint is a particularly useful comparison for NSH: it also connects to Rust, supports fine-grained bindings and offers a runtime interpreter. The trade-offs concern what newly delivered programs contain, how the host integrates them and which layer manages lifecycle and policies.

| Dimension | NSH mechanism | Slint mechanism | Practical difference and integration cost |
| --- | --- | --- | --- |
| Delivered interface program | TSX packages organize state, Promises, asynchronous operations and events, running in QuickJS | Usually compiles `.slint` into component types; the [interpreter](https://docs.slint.dev/latest/docs/rust/slint_interpreter/) can also build components from source or files, set properties and attach callbacks | Both can generate interactions at runtime. NSH delivers general-purpose TSX modules; Slint uses its own UI language and connects business logic through host callbacks |
| State evaluation and layout | A signal graph tracks dependencies, with Taffy layout after binding updates | Slint marks bindings dirty by dependency and [re-evaluates them lazily](https://docs.slint.dev/latest/docs/slint/reference/language/evaluation-and-purity/) when read; layout uses minimum, maximum and preferred sizes plus stretch constraints | Both are fine-grained models, with different evaluation and layout rules. Evaluate how naturally they express components and task logic rather than reducing the choice to re-rendering behavior |
| Scheduling | Each native dynamic surface has a separate engine thread, and the UI thread applies batches | Components are typically used on the UI event-loop thread; background results return through [invoke_from_event_loop](https://docs.slint.dev/latest/docs/rust/slint/) | NSH gives script modules a separate scheduling unit. Slint hosts must schedule expensive work, and NSH native callbacks likewise need their own handling of blocking work |
| Object and callback lifecycle | Surfaces manage modules and nodes; host-registered objects retain responsibility for their resources | [ComponentHandle](https://docs.slint.dev/latest/docs/rust/slint/trait.ComponentHandle) is a strong reference; callback captures typically use [Weak](https://docs.slint.dev/latest/docs/rust/slint/struct.Weak), and cross-thread updates enter the event loop | Slint's lifecycle rules are explicit and controllable. NSH centralizes module lifecycle in the surface, while asynchronous callbacks and host resources still require coordinated cleanup |
| Package acceptance and permissions | APIs cover signatures, revocation, rollback, capability intersection and VM limits | The interpreter provides compilation, import and component APIs; import hooks can restrict sources, while independent package trust, permissions and budgets are implemented by the host | NSH reduces the work needed to build a policy layer for partner modules. Slint hosts can implement these policies too; the frameworks take responsibility for different scopes |
| Rust computation and drawing | Rust core components are available to TSX; host platform views integrate through registration APIs | Rust property and callback APIs connect to business logic; Rust-generated pixels can be displayed through [SharedPixelBuffer/Image](https://docs.slint.dev/latest/docs/rust/slint/struct.Image), or drawing can integrate with the renderer | Both support Rust computation. Existing Slint components can be retained directly; NSH lets dynamic task modules and Rust capabilities share its component model |
| New native capabilities | Update the host binary, then allow modules to call them | Interpreting `.slint` dynamically uses the native implementations already available in the host | Both are constrained by host APIs and binary compatibility. NSH dynamic packages retain the native release process for new native implementations |
| Mobile and Web | iOS/Android backends and an HTML/DOM Web path | Slint has [Android](https://docs.slint.dev/latest/docs/slint/guide/platforms/mobile/android/) and [iOS](https://docs.slint.dev/latest/docs/slint/guide/platforms/mobile/ios/) paths; [Web](https://docs.slint.dev/latest/docs/slint/guide/platforms/web/) renders through Canvas | The differences lie in platform integration and presentation models. Existing Slint products should compare specific input, rendering and embedding requirements; Slint supports both mobile and browser targets |

**Generating the same order confirmation interface:** Slint's interpreter can construct a new interface with handler logic and connect it to a host save-order callback. NSH can organize asynchronous queries and event flows in TSX, then call registered APIs. For complex general-purpose task logic, NSH's language and module execution path are more direct. When existing Slint components and callbacks already express the requirements, retaining them keeps the existing runtime model.

**Reusing the same Rust chart:** both Slint and NSH can retain Rust computation and drawing implementations. NSH offers its established surface package and host capability contracts; Slint offers existing native components and APIs plus a compiled execution option. Both need explicit integration of drawing resources, threads and teardown responsibilities. A shared implementation language still leaves that integration work to do.

## Dynamic capabilities and a compiled core

Dynamic interfaces need flexibility, while core features need predictable implementations. NSH lets an application choose the execution path for each.

| Feature layer | Implementation options | Delivery and execution |
| --- | --- | --- |
| Core business logic and computation | Rust modules, types and background tasks | Compile to machine code on native platforms and expose calling interfaces through the host |
| Complex or frequently updated UI | Rust components or existing host-native components | Keep the core implementation native and let dynamic modules organize interaction |
| AI-generated pages | Dynamic TSX modules | Deliver state, layout and behavior for each task |
| Complete application | Pure Rust, TSX or a mixed implementation | Choose the scope of dynamic capabilities to suit the product |

[Pure Rust applications](./rust.md) can omit QuickJS entirely; mixed applications retain it for dynamic TSX. Charts, editors and data-processing features can remain in Rust, with dynamic modules handling page composition and task interactions.

On native platforms, Rust UI and business logic compile to machine code. Their execution is independent of JavaScript engine performance, with direct access to Rust's memory management and low-level optimization capabilities. Dynamic modules can focus on page composition while core implementations evolve to meet their own performance requirements. The final interface experience still needs to be measured in the target product and on its devices, accounting for layout, text, drawing and platform integration.

## Platform paths

| Platform | NSH presentation path | Integration |
| --- | --- | --- |
| iOS | UIKit and CoreText | Embed in a native app or build a standalone application |
| Android | Android Views with platform text and input integration | Embed in an existing client or build a standalone application |
| macOS | AppKit, Core Animation and CoreText | Embed in or build a desktop client |
| Windows | A retained view tree in Win32, drawn with Direct2D and DirectWrite | Embed in or build a desktop client |
| Linux | GTK 4, custom GSK drawing and Pango text | Embed in or build a desktop client |
| GPUI | An NSH view tree drawn through the GPUI backend | Embed in GPUI and GPUI Kit products |
| Web | HTML and DOM | Publish a web interface or integrate with an existing page |

NSH shares component abstractions and a development model while using implementations suited to each platform. The use of operating-system controls and the behavior of individual components vary by platform. Check the [platform guides](./platforms.md) against your application's requirements.

On [Web](./web.md), both Rust and TSX applications render HTML. Dynamic TSX uses QuickJS; pure Rust applications can omit that dependency. Browser presentation and the language used to execute application logic are separate choices.

## Which products suit NSH?

| Product need | How to use NSH | What to evaluate |
| --- | --- | --- |
| AI assistants that generate actionable results | Deliver forms, filters, lists and step-by-step interfaces | Generated-code checks and host business authorization |
| Mobile clients with context-specific pages | Dynamic modules call host-exposed services | Platform policies, module trust and available native capabilities |
| Desktop plugins and workflow extensions | Organize modules with signed packages and surface policies | Update compatibility, lifecycle and resource budgets |
| Existing native products adding AI capabilities incrementally | Start with one panel or page | Embedding APIs and cooperation with existing pages |
| GPUI products that need dynamic interfaces | Keep the application core in Rust and embed NSH surfaces | Host capability registration and actual platform integration |
| Complete Rust clients | Build UI and business logic in Rust, adding dynamic modules where useful | Required components, platform behavior and measured performance |
| Interactive entry points on mobile, desktop and Web | Use the shared component model and platform backends | Differences in input, navigation, presentation and integration |

NSH's core value is to give applications new interactive capabilities at runtime while keeping the host in control of features, permissions and implementation choices. Start with an AI-generated dynamic panel or use the same capabilities to build a complete client. Evaluate this delivery path alongside your team, existing components and platform requirements to establish what it can bring to the product.
